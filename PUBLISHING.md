# Публикация релиза

Репозиторий: [average-vibecoding-enjoyer/pinus-smart-awg](https://github.com/average-vibecoding-enjoyer/pinus-smart-awg). Бинарники распространяются как GitHub Release assets; исходники, лицензии и инструкции хранятся в Git.

## Preview 3.3.3: готовые проверенные пакеты

Этот выпуск публикуется вручную с тегом **`v3.3.3-preview`** и отметкой **Pre-release**. Теги `*-preview` исключены из автоматического workflow `Release`, чтобы публикация не запускала повторную сборку и не подменяла уже проверенные пакеты.

Бинарники собраны 2026-09-14 из commit `b9c29cc01d11c4e5d56b2b5436607da6b432d739`. Публикация 2026-09-21 добавляет оформление и публичные метаданные. Тег публикации может указывать на более поздний commit документации; поле `source_commit` в manifest должно сохранять фактическую ревизию бинарников.

1. Проверьте состав и SHA-256 готовых пакетов. Не запускайте установщик или VPN для публикации. Существующие MSI, portable ZIP и соответствующие архивы исходников должны сохранить исходное содержимое.
2. Подготовьте отдельную папку только для публичных assets: MSI и portable ZIP Windows x64, `Pinus-Smart-AWG-Preview-3.3.3-source.zip`, `amnezia-box-Pinus-Preview-3.3.3-source.zip`, публичный `release-manifest.json` и `SHA256SUMS.txt`. Последний должен содержать суммы только публикуемых файлов, без самого файла контрольных сумм.
3. В публичном manifest сохраните версию, дату сборки, исходную ревизию, зависимости и контрольные суммы. Удалите локальные пути, данные процессов и ссылки на непубликуемые журналы `evidence/`. Сохраните `signed: false` и различие между тестами в памяти и проверкой настоящей сети. Полную исходную локальную диагностику оставьте отдельно.
4. Обновите README, CHANGELOG и `.github/release-notes/v3.3.3-preview.md`. Проверьте точные имена файлов и тег в ссылках. Не объявляйте Preview стабильным выпуском или универсальным исправлением сетевых ошибок.
5. Выполните `scripts/scan-secrets.ps1`, просмотрите diff и состав архивов, затем отправьте commit публикации и тег `v3.3.3-preview` в этот репозиторий.
6. Создайте черновик GitHub Release с заголовком **Pinus Smart AWG 3.3.3 Preview**, отметкой Pre-release и описанием из `.github/release-notes/v3.3.3-preview.md`. Приложите только подготовленные публичные assets. Не помечайте этот выпуск как Latest стабильной ветки.
7. Проверьте assets и описание черновика, опубликуйте его и проверьте доступность страницы и загрузок. Публикация не устанавливает клиент и не меняет работающее VPN-подключение.

Архив исходников клиента соответствует готовым бинарникам; автоматически создаваемый GitHub архив тега также содержит более позднее оформление публикации. Полный архив изменённого движка и его лицензия обязательны в комплекте с бинарником.

## Подписанные пресеты маршрутизации

Клиент принимает сетевые пресеты только после проверки встроенным публичным
ключом Ed25519. Приватный ключ не хранится в репозитории: локальный инструмент
шифрует seed через Windows DPAPI, поэтому использовать его может только тот же
пользователь Windows на этом компьютере.

Первичная генерация ключа выполняется один раз:

```powershell
cd client
go run ./cmd/preset-sign -mode generate `
  -key "$env:USERPROFILE\.pinusvpn-signing\preset-ed25519.dpapi"
```

Для обновления увеличьте ревизию, сформируйте payload и подпишите его:

```powershell
go run ./cmd/preset-sign -mode export -revision 3 `
  -published-at "2026-07-11T15:30:00Z" `
  -output "..\presets\catalog.json"
go run ./cmd/preset-sign -mode sign `
  -key "$env:USERPROFILE\.pinusvpn-signing\preset-ed25519.dpapi" `
  -input "..\presets\catalog.json" `
  -output "..\presets\catalog.signed.json"
go test ./smart
```

Коммитьте оба файла из `presets/`. Никогда не добавляйте `.dpapi`-ключ. Клиент
не принимает откат ревизии, неизвестные поля, опасные системные процессы,
некорректные домены, слишком большой payload или неверную подпись.

## Следующие обычные релизы

1. Обновите номер в `client/version/version.go`, `client/versioninfo.json`,
   `client/manifest.xml`, `packaging/README.txt` и добавьте заметки в
   `.github/release-notes/vX.Y.Z.md`.
2. Локально запустите `./build-public-release.ps1 -Architectures amd64`.
   Другие архитектуры добавляйте только после отдельных проверок.
3. Проверьте `release/release-manifest.json` и `release/SHA256SUMS.txt`.
4. Для публичного продукта подпишите клиент и MSI сертификатом подписи кода.
5. Создайте и отправьте обычный тег вида `vX.Y.Z`. Workflow `Release` пересоберёт
   и приложит все артефакты автоматически. Не создавайте параллельно второй ручной
   релиз с тем же тегом. Теги `*-preview` обрабатываются вручную, как описано выше.

Для подписанного релиза добавьте в GitHub Actions Secrets:

- `WINDOWS_SIGN_CERT_BASE64` — PFX-сертификат в Base64;
- `WINDOWS_SIGN_CERT_PASSWORD` — пароль PFX.

Workflow импортирует сертификат только во временное хранилище runner и удаляет
файл PFX сразу после импорта. Без этих secrets сборка останется рабочей, но
будет опубликована без подписи и может вызвать предупреждение SmartScreen.

Папки `release/` и версии `release-*` намеренно игнорируются Git. MSI, ZIP, архив исходников
движка, manifest и checksums загружаются как GitHub Release assets, а не
коммитятся в историю исходников.

Перед публикацией нельзя добавлять:

- `.conf`, приватные ключи и runtime JSON;
- содержимое `diagnostics/`, локального `evidence/` и локальные журналы;
- API-токены, пароли серверов и сертификаты подписи;
- тестовые скриншоты с профилями, адресами или именами пользователей.

Обезличенное описание проверок публикуется отдельно от исходной диагностики.
